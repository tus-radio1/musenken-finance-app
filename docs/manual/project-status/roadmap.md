- ~~R5: 予算ページでは会計に編集ボタンを表示しているのに、サーバー側は拒否する。この食い違いを直す。~~ **PR-A で対応**：予算の編集は管理者が常に、会計が現在の年度のみ。班長は不可。会計年度はサーバー側で確認する。
- 取引の登録先・移動先の班に対する権限チェック：**アプリ側は PR-A で対応**。DB 側（`transactions_insert_member` の条件が常に真になっている問題と、移動先の確認）は PR-B。
- 承認：**PR-A で対応**。承認者は管理者と会計のみで、班長は承認できない。自分の申請は誰も承認できない。過年度の承認は管理者のみ。編集フォームから承認ステータスを直接変えられるのは管理者と会計で、会計は自分の取引を変更できない。管理者が自分の取引を修正する場合は、監査ログを先に記録できたときだけ変更する。会計による自己承認を DB でも拒否する変更は PR-B。
- 0 行しか更新・削除されなかった書き込みを成功扱いしていた箇所（承認、取引の編集・削除、補助金の更新・削除、部員の更新・退部）：**PR-A で対応**。申請者本人による補助金の削除が効いていなかった問題は、ポリシーの追加（`20261022140000`）で直した。
- 会計を全体管理者から分離し、他人の承認済み取引の削除・補助金の論理削除・会計グループと年度の管理を明示的に許可。財布編集・過年度予算編集と承認・自己取引の特別修正・役員任命は管理者のみ（適用順：権限追加マイグレーション→アプリ→ロール種別修正）。
- 部長・副部長に部全体出納帳の閲覧権限を追加。取引・資金移動・財布の書き込みは許可せず、一般部員には公開しない。
- **PR-B 対応済み（実装・ローカル検証）**：DB でも会計の自己承認・申請者と承認者の不正変更・所属外の制限付き班への登録と移動を拒否。過去データの通常編集と管理者の自己行修正は維持する。develop → main の順で反映し、本番 DB デプロイは承認が必要。
- 未対応：部員の削除（`deleteMember`）は、非管理者が実行するとロールの削除とプロフィールの論理削除が 0 行になる。続く Auth ユーザーの削除でプロフィールが連鎖して物理削除され（取引がある部員では Auth の削除が失敗する）、論理削除の意図どおりにならない。次の対応候補。
